# 서버 2 공유 챕터와 이야기

2026년 11월 21일 PM 요구사항의 공유 챕터 구조를 기준으로 구현했다. 서버 1의 공통 API 브랜치를 기반으로 작성했으며 JdbcClient와 기존 세션·책 접근 검사·응답 래퍼를 재사용한다.

## 호출 순서

1. 서버 1 API로 두 사람이 책에 연결한다. 책 생성 시 기본 ‘초등학생 시절’ 챕터 하나가 생긴다.
2. GET /api/v1/books/{bookId}/chapters로 목록과 챕터 ID를 얻는다.
3. 각자 PUT /api/v1/chapters/{chapterId}/story로 자기 이야기 전체를 저장한다.
4. POST /api/v1/chapters/{chapterId}/story/complete로 각자의 작성을 완료한다.
5. 두 사람이 모두 완료하면 챕터 조회의 receivedMission에 상대 미션 문구가 표시된다. 상대 이야기 본문은 계속 null이다.
6. 각자 상대 미션을 수행하고 PUT /api/v1/chapters/{chapterId}/reflection에 `{ "content": "느낀 점" }`을 보낸다. 첫 제출부터 `progress[].reflectionCompleted`가 true가 되므로 미션을 준 사람은 완료 여부를 알 수 있다. 상대 감상 본문은 여전히 null이다.
7. 두 사람이 모두 감상을 제출하면 두 번째 요청 안에서 챕터가 열린다. `openedAt`이 채워지고 양쪽의 이야기와 감상이 보인다.

이야기 저장 입력 예시는 다음과 같다. PUT은 전체 저장이며 생략한 값은 빈 문자열이 된다.

```json
{
  "title": "첫 월급을 받던 겨울",
  "content": "퇴근 버스에서 노래를 들으며 집에 갔다.",
  "missionInstruction": "퇴근길에 좋아하는 노래 한 곡을 들어봐."
}
```

이름 최대 100자, 이야기 제목 200자, 본문 20000자, 미션 2000자를 제안값으로 적용했다. 임시저장은 빈 값으로 가능하고, 작성 완료는 제목·본문·미션이 모두 채워져야 한다. 두 사람이 모두 작성을 완료해 미션이 상대에게 공개된 뒤에는 미션 문구를 바꿀 수 없다. 기존 문구를 그대로 보내면 제목과 본문은 챕터가 열리기 전까지 수정할 수 있다.

열리기 전 목록과 상세는 myStory와 myReflection에 현재 참여자 본인의 내용만 반환한다. progress에는 두 사람의 이야기 완료 여부와 감상 제출 여부를 포함하되 상대 본문은 포함하지 않는다. nextAction은 WRITE_STORY → WAIT → DO_MISSION → WAIT_FOR_OPEN → READ로 변한다. 상대 이야기와 감상은 READ에서만 반환한다.

감상은 제목 없이 본문 하나이며 공백을 제외한 최대 10000자다. 상대 미션이 도착한 뒤 제출할 수 있고, 챕터가 열리기 전에는 같은 PUT으로 수정할 수 있다. 최초 제출 시각은 유지된다. 챕터가 열린 후에는 이야기와 감상 모두 수정할 수 없다. 두 감상 제출은 챕터 행 잠금과 MySQL `READ COMMITTED` 트랜잭션으로 직렬화해 공개 시점을 결정한다.

빈 챕터는 두 참여자 누구나 DELETE /api/v1/chapters/{chapterId}로 삭제할 수 있다. 제목·본문·미션 중 하나라도 있거나 작성 완료 이력이 있으면 409다. 저장·완료·삭제는 같은 챕터 행을 잠가 경쟁 요청을 순서대로 처리한다.

## 남은 범위

읽음 상태, 푸시, 이야기 삭제는 후속 구현이다. 본문과 음악을 미션과 함께 즉시 공개하던 이전 ERD·API 초안은 이 구현의 기준으로 사용할 수 없다.

Swagger UI에서 ‘챕터와 이야기’를 선택하면 7개 API를 확인할 수 있다. 서버 1의 MySQL 8 V1을 기준으로 V2·V3를 적용한다. 배포 전후에는 마이그레이션과 프론트 origin의 PUT·DELETE CORS 허용을 확인한다.
